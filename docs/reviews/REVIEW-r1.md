## Independent cold-start answer

Question: What does bbhost publicly document about game-owned GX identities and writes, and what observation is needed before treating it as a safe lifetime contract elsewhere?

At `566184a74f071166299bb656c4af479e5bbe2771`, the [GX header](https://github.com/droogie/bbhost/blob/566184a74f071166299bb656c4af479e5bbe2771/src/engine/gx_resources.h) declares resource records and address/range lookups. Its comments describe a game id distinct from storage address, a new id for later reuse of storage, and registry write tracking for initial data and Map events. These are author-reported semantics, not an independently inspected implementation or run. RC-0001 correctly separates that from the declared interface.

Phase and field limits matter: object registration is described at creator return; id 0 can mean creation was unseen. `alive` is registry state, not GPU completion. Protection notifications are not proof of content writes. A zero creation-failure count can mean the registry is disabled. `created_flip` alone gives neither a fence nor a safe retirement point. The header does not establish complete write/alias coverage or wrap safety. No counterpart cache identity in another port was inspected. The [rendering document, lines 20-25](https://github.com/droogie/bbhost/blob/566184a74f071166299bb656c4af479e5bbe2771/docs/rendering.md#L20-L25) describes collecting inputs at GX hooks and later command-token consumption; that is project documentation, not evidence that all consumers have finished.

**Proposed useful positive, not performed:** in one authorized exact-build/platform experiment, follow a naturally reached successful GX creation with initial data, one actual content mutation and a named draw/dispatch consumer. Observe original producer events and sampled raw fields at creator return, after mutation, at consumer capture/submission, at completion and at destruction/unmap. Bind holder, logical id, storage range, independent content evidence, host/cache object version and completion evidence. Show the consumer received the expected version and old consumers completed before retirement; then reuse the same storage and demonstrate a distinct new identity/version. Compare original events with observer records rather than generating expectations from the observer itself. This supports only that selected lifecycle.

**Proposed falsifier, not performed:** after retirement/reuse of the same address, an independently observed consumer still needs the old resource while the registry/cache treats it as dead or selects the new resource because of address equality. That contradicts the proposed safe-retirement/identity contract even if checker flags pass. Raw-field contradictions also need to be discriminated: changed content without a write-sequence advance (for example an uncovered alias/GPU write) defeats content authority; a protection change or Map without an actual mutation must not by itself prove new content. Unseen id 0 and a failure count of 0 while disabled are unknown evidence, not healthy-resource positives.

The next action is an implementation/observer-coverage inspection for one selected producer and consumer, followed only in the owning project by an explicitly authorized game-reached lifecycle observation. This Commons release does not need to run or build that experiment.
