## Checked contract and supported conclusions

The consumer is a maintainer deciding regular-path module reuse after one live descriptor/render change. I read Commons instructions, evidence policy, continuation rules, the complete dossier, both claims, frontier, author receipt, and the complete relevant delta. I independently followed the actual primary producers, comparison phase, compilation influence and selected binding consumers; author checker output was not the semantic oracle.

**Program producer and identity.** `SearchBinaryInfo` checks its signature and `GetParams` copies `BinaryInfo.shader_hash` with code/user-data spans (`regs_shader.h` 16–39, 224–250). Regular `GetProgram` searches the `size_t` program map with that metadata value (`vk_pipeline_cache.cpp` 1113–1144; header 42–69, 192–211). This is not a recomputed current-byte hash, stage-identity proof, authenticated header, collision guarantee or portable-width ABI. New-program resource analysis precedes stored specialization. On an existing program, base/user data and flattened words refresh before current specialization. The candidate describes those facts and limits accurately.

**Directional module selection.** The explicit last-used check is stored-left/current-right (1151–1155). The list lookup supplies stored module specialization as its projection and current specialization as the value. The inspected standard-library `ranges::find` implementation compares `invoke(proj, *first) == value`, consistent with that expression order; this supporting static read does not establish the toolchain of a built upstream binary. `StageSpecialization` 197–248 rejects invalid left `info`, compares vertex attributes/runtime/fetch/FMasks, then accepts if both validity bitsets are empty. Otherwise starts must match; buffer/image comparisons use current validity bits, while sampler comparisons have no such guard. Pointer identity and bitset equality are absent. Equal layout/list lengths and valid produced records are essential; the candidate does not promise arbitrary-record safety or sampler-only correctness.

**Valid descriptor controls.** `SharpFetch` and `BufferResource::GetSharp` read loaded/immediate words, apply post-operations and reject failed/type-invalid fetches (`resource.h` 24–104). Buffer truthiness is nonzero record count, distinct from type validity (`amdgpu/resource.h` 48–54). Specialization construction sets bits only for truthy sharps and derives stride, paging, usage-formatted flag and swizzle state. Formatted usage is analyzed from instruction opcodes and OR-merged on shared resources (`resource_patching_pass.cpp` 98–113, 183–216); the dossier correctly avoids treating it as a freely changed live descriptor field.

For its stated successfully compiled raw-U32 vertex-program premise, descriptor stride 16 to 32 with count 64 produces sizes 1024/2048, stays truthy/nonpaged and rejects the old module. Address lowering independently embeds the stride (`resource_patching_pass.cpp` 546–635); with index 3 and zero offsets, the element-address arithmetic is 12 versus 24. This supports a meaningful negative against reuse of that old module. If no other compatible module exists, the source attempts compilation; successful translation/module creation, compatible pipeline creation and safe execution remain separate unobserved facts.

The corresponding positive ignored-format control is source-compatible: under unchanged analyzed raw-U32 usage, swizzle off, fixed stride/count/type/base/layout/runtime/start/profile and no fetch-attribute overlap that changes earlier comparisons, constructor/equality omit descriptor format/number/destination-select fields and `BufferAddressShift` takes the raw-U32 default shift 2 (49–94). Those raw words can vary through loaded flattened data. This does not certify arbitrary formats, other usage, resource contents or full compiler correctness. Size and paged classification depend on stride/count/base rather than these fields in the inspected buffer producer. The ordinary selected binding reads its current sharp and resolves the current address/range (`vk_rasterizer.cpp` 3075–3155), so reuse is not proof of old data reuse or allocation lifetime.

The other grouped source controls agree with the raw predicates: swizzle-off index-stride changes are ignored, swizzle-on changes compare and lower `8 << index_stride`; address/count changes are eligible only while the relevant truthiness/paged classification and earlier inputs match; stride-zero count crossing 64 MiB changes paging when enabled. Stored-bound/current-unbound skips that buffer, while the reverse default-stride/current-bound case rejects. Both-empty starts bypass the start check; bound starts do not. These conditional cases preserve producer-compatible loaded words and matching analyzed layouts rather than inventing independent formatted flags. No serialized fixture was produced.

**Pipeline phase and byte identity.** Graphics refresh zeroes its key, fills render information and selects stages before ordinary graphics-map lookup (720–1023, 527–544). Graphics equality is full-object `memcmp` and the hash covers full bytes; it includes padding/build representation, not merely a semantic field list (`vk_graphics_pipeline.h` 32–70, 133–138). Construction and refresh zeroing are verified, but cross-build/padding portability is unqualified. Same stage values with different producer-selected polygon mode reject the old key; the pipeline constructor consumes polygon mode (97–112). An unchanged full key makes its existing map entry selectable. A module hit alone proves neither of those outcomes. Pending/asynchronous branches may return null or wait; pipeline creation can fail.

Prepared selection is a separate phase: copied analyzed Info, shared program lookup, refreshed flattening, existing-module-only search and failure when unavailable (1072–1110). Prepared GPU acceptance additionally requires Ready/checksum, program values, base and flattened-byte checks before map lookup (446–485). The candidate correctly keeps these prerequisites separate from a regular hit.

**Profile, persistence, invalidation and ownership.** One cache constructs its profile from device/compiler/environment/memory-mode inputs before warmup; the inspected class exposes a const profile reference and no profile-changing method. Same-instance premises are appropriate; missing live full-profile comparison alone is not a staleness proof. Warmup requires exact profile-record size, magic and binary/meta/key versions 9/7/5 plus declared-field profile equality (serialization 329–376). A matching record permits subsequent entry loading; missing/mismatched records request clear/FinishPreload/profile save and return before entry loading. Individual metadata/binary/ordinal checks, motion-vector rejection, SPIR-V header requirement and exception cleanup were traced. These gates do not prove arbitrary SPIR-V validity, driver version/UUID portability, cross-ABI persistence or original-image identity.

The driver pipeline-cache handle is separate and is created after warmup (290–367). Renderer records serialize metadata/SPIR-V/pipeline construction inputs; the selected path does not import/export a driver cache blob. `DataBase::Clear` returns immediately in archived mode (278–297). Save queues work (140–182, 207–224); stop/join/finalize is not a readback/durability receipt. Patch selection occurs during module compilation, and explicit `ReplaceShader` dependency removal relies on its conditional related-pipeline map. The candidate retains these limits and does not claim complete invalidation, synchronization or in-flight lifetime safety.
