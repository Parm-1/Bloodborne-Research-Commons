## Fresh-reader answer

The `0x400000` difference is only a candidate coordinate conversion. The pinned bbport producer returns `text` bytes, ELF `tva`, and function starts `hva + loc`; its scanner computes call-site and caller values in the same ELF VA coordinates and applies no image digest or base conversion ([`tools/re/callgraph.py`, lines 10–26, 29–49](https://github.com/deadinside28/bloodborne_pc/blob/3c57da4198ad62039f63f33bfd205b9916518acf/tools/re/callgraph.py#L10-L49)). The pinned bbhost helper defines `kBase = 0x400000` as its Binary Ninja image base and the slide used by `load()` ([`eboot_kit.h`, lines 27–39](https://github.com/droogie/bbhost/blob/566184a74f071166299bb656c4af479e5bbe2771/tests/decomp/eboot_kit.h#L27-L39); [`eboot_kit.cpp`, lines 181–188](https://github.com/droogie/bbhost/blob/566184a74f071166299bb656c4af479e5bbe2771/tests/decomp/eboot_kit.cpp#L181-L188)). Its `file_at` subtracts that base before PT_LOAD file mapping, and its function table adds it to the start while leaving size unchanged ([`eboot_kit.cpp`, lines 59–72, 131–165](https://github.com/droogie/bbhost/blob/566184a74f071166299bb656c4af479e5bbe2771/tests/decomp/eboot_kit.cpp#L59-L72); [`eboot_kit.cpp`, lines 131–165](https://github.com/droogie/bbhost/blob/566184a74f071166299bb656c4af479e5bbe2771/tests/decomp/eboot_kit.cpp#L131-L165)). Thus `BN - 0x400000 = ELF_VA` is supported for this helper's declared coordinate convention, subject to valid domain and mapping.

Identifying the same **original-image address point** additionally requires both records to establish the same original input bytes (digest plus build/view context), producer and raw field provenance, explicit coordinate origins, and a reversible conversion whose PT_LOAD file/VA mapping agrees and is unambiguous. If those premises hold and normalized points match, the guide permits `JOIN_SUPPORTED_UNDER_PREMISES` for the point. To claim the same described extent, compatible independently supported start/range records are also required. Neither an address-point match nor an FDE proves a complete logical function identity; that needs entry/symbol/disassembly evidence. The guide states these distinctions and limits at [`knowledge/function-address-correspondence.md`, lines 7–25, 45–53](https://github.com/Parm-1/Bloodborne-Research-Commons/blob/790ff6608cae66f8e73519932b51e4b7282c06e0/knowledge/function-address-correspondence.md#L7-L53).

A concrete invalid join: the guide's hypothetical start `0x2120` and kit coordinate `0x402120` normalize numerically, but if one report is bound to hypothetical digest H/build Q and the other to J/build R, same-original-image correspondence is `CONFLICT`; if either digest is missing, it is `UNKNOWN`. Likewise, in the example segment (`p_offset=0x1000`, `p_vaddr=0x2000`), `V=0x2120` maps to `O=0x1120`; a claimed file offset `0x1220` is a contradictory mapping. These are expressly invented metadata, not game records or producer executions ([guide, lines 55–63](https://github.com/Parm-1/Bloodborne-Research-Commons/blob/790ff6608cae66f8e73519932b51e4b7282c06e0/knowledge/function-address-correspondence.md#L55-L63)). The example is a sound invalid-join counterexample: numeric normalization cannot cure different image identity or inconsistent segment/file mapping.

“No callers” from this scanner cannot establish unreachable code. The script scans raw `E8` and `E9` bytes in the first executable segment, uses unwind-table starts as targets, and records hits only when a containing source range is selected; it does not decode instruction boundaries. It omits the last five possible byte starts and indirect calls; `E9` is a jump candidate, not a call. Earlier RC-0003 also limits coverage to that segment and described unwind functions ([`callgraph.py`, lines 14–26, 33–49](https://github.com/deadinside28/bloodborne_pc/blob/3c57da4198ad62039f63f33bfd205b9916518acf/tools/re/callgraph.py#L14-L49); [`RC-0003`, lines 17–25](https://github.com/Parm-1/Bloodborne-Research-Commons/blob/790ff6608cae66f8e73519932b51e4b7282c06e0/claims/RC-0003-callgraph-limits.md#L17-L25)). Absence of an observed candidate is therefore missing observation under a bounded scanner, not evidence of absence of a real edge or reachability.

It also cannot establish decompilation completion. RC-0003's appended extension says counts refer to retained byte-site occurrences, distinct caller-start sets and a union; duplicate rows may remain, printed per-function callers are truncated to 20, and no output path suppresses detailed caller lists ([`RC-0003`, lines 33–43](https://github.com/Parm-1/Bloodborne-Research-Commons/blob/790ff6608cae66f8e73519932b51e4b7282c06e0/claims/RC-0003-callgraph-limits.md#L33-L43)). None is a completion denominator. Nor does an address or unwind match establish runtime/replacement equivalence: the bbhost load path maps and relocates a loaded image and `stub()` patches code ([`eboot_kit.cpp`, lines 181–218](https://github.com/droogie/bbhost/blob/566184a74f071166299bb656c4af479e5bbe2771/tests/decomp/eboot_kit.cpp#L181-L218)); runtime claims need loaded-image digest, actual slide and patch history plus ABI/input/state/path and attributable runtime comparison evidence. The guide explicitly stops those stronger claims at UNKNOWN absent such evidence ([guide, lines 29, 49–53, 70–73](https://github.com/Parm-1/Bloodborne-Research-Commons/blob/790ff6608cae66f8e73519932b51e4b7282c06e0/knowledge/function-address-correspondence.md#L29-L29)).
