## Question 1: Closing two readers after a discarded texture record

Source facts. With BBHOST_GPU_UNTILE=1 (the default), BBHOST_UNTILE_VRAM on, and the device-local route selected, this upload has two guest-source readers. Reader B is a hash-only prep. It is queued on PrepPool with hash_only set and no destination, and it reads guest bytes for the sampled/exact content hash and the exact hash. It is never added to g_batch_preps ([textures.cpp lines 1131-1135 and 823-852](https://github.com/droogie/bbhost/blob/566184a74f071166299bb656c4af479e5bbe2771/src/host/textures.cpp#L823-L852)). Reader D is the vkCmdCopyBuffer fetch that copies the guest source into device-local scratch ([line 1165](https://github.com/droogie/bbhost/blob/566184a74f071166299bb656c4af479e5bbe2771/src/host/textures.cpp#L1165)). The untile compute reads scratch, so it is not a guest reader on this route. There is no inline CPU reader and no batch prep for this upload.

Case A. Both readers are closed on the supplied premises. A worker publishes state 2 only after run_prep returns, and a completed wait on that prep cannot return earlier. The attributable state-2 record therefore closes B, including its second hash read. The successfully completed fence of the submission containing the fetch closes D. Surface erase fills no gap, because it only drops a reference and cancels nothing. The pre-submit staging wait fills no gap either, because textures_before_submit waits only the entries of g_batch_preps and B is not one of them. The developer can say that this upload's two guest-source reads have ended. That still does not justify releasing or reusing the allocation. The owner's rule must keep that memory readable and authoritative through both reads and must order permitted writers. Smallest source-only continuation: search the pinned public decomp for the original texture allocator's free or recycle body and check whether it reaches a wait on this prep or a job barrier. The dossier says the inspected paths do not contain that body, so this is a search that may come back empty. Falsifier of "all source reads have ended": an attributable observation that the same job is in state 0 or 1 after the recorded state 2, or a fetch or hash read of this upload's range recorded after the claimed fence completion.

Case B. Only D is closed. The fence covers the submitted fetch. The new Surface's prep is a different object, even at the same guest address, and RC-0007 states that a new prep at the same base is not the old job. Reader B is therefore unknown. The old job may still be queued or running and may be reading memory that now belongs to another allocation. Surface erase and the batch wait do not change this. The developer cannot claim that B ended. The next step is to recover the old job reference, for example one a caller kept before the Surface reset, and observe or wait on it. Source-only check: confirm whether any caller path keeps the old TexturePrep pointer after the Surface reference is reset. If none does, B has no observable completion in the inspected code. Falsifier of "ended": any observation of the old job in state 0 or 1 at a time the claim says it had finished.

Case C. Only D is closed. A state-1 observation means a worker has claimed the job but has not published state 2. Since state 2 follows the reads, the second hash read may still be running at the observation point. The developer cannot conclude that B ended, and the claim is false at that instant. The next step is to keep observing the same job reference until it reaches state 2, or to wait on it. Falsifier of "ended": a later state-1 observation of the same job with no later state-2 record.

Applicability: bbhost pin, Linux x86-64 Vulkan, default untile mode 1, device-local route. Evidence is source control flow only.

## Question 2: Interpreting constructed comparison data, then planning a real check

Configuration. The bbhost pin, Linux x86-64 AVX/SysV, UNIX target, default GS mode (BBHOST_TLS_GS unset or not beginning with 0), fixed 0x400000 mapping, default 2000 cameras by 60 frames, seed 0xca3e7a, and the kit's collision, debug, and math substitutions. Camera words use bit equality, except that any two NaN encodings count as equal. The first 0x20 GSM bytes use raw memcmp with no NaN exception ([comparators](https://github.com/droogie/bbhost/blob/566184a74f071166299bb656c4af479e5bbe2771/tests/decomp/follow_camera_test.cpp#L355-L365); [dossier matrix](https://github.com/droogie/bbhost/blob/566184a74f071166299bb656c4af479e5bbe2771/tests/decomp/follow_camera_test.cpp#L543-L558)).

Case A. The camera NaN exception applies, so the camera gate passes. GSM is identical and no other category differs, so this frame is consistent with the declared relation. It does not establish byte identity. The word relation accepts any two NaN encodings by design, so 0x7fc00110 against 0xffc00420 is an intended blind spot. Case A supports only "equal under the camera-word relation."

Case B. All camera words are identical, but the raw GSM comparison fails on the NaN slot, because the NaN exception does not apply to GSM. The frame counts as a failure: bad rises once, and detail is recorded for the first 12 failing frames. The camera_same gate covers both camera and raw GSM, so the test copies B's camera from A to resynchronize. It does not copy GSM and does not reset bad. Later agreement cannot erase the earlier failure, and the final exit stays 1. Later agreeing frames only show the post-resync trajectory.

Case C. "Zero differences" by itself establishes nothing. A selected pass requires exit 0, bad equal to 0, and nonzero mouse-turn, held-frame, and Original-tuning counters ([outcomes](https://github.com/droogie/bbhost/blob/566184a74f071166299bb656c4af479e5bbe2771/tests/decomp/follow_camera_test.cpp#L549-L595)). Zero differences with zero counters is an incomplete gate and exits 1. An identity skip (77), a loader or setup failure (1), an unbound-import abort, or an undersized argument run could each be summarized as "zero differences." The phrase cannot tell these apart.

Prospective check, not authorized and not executed. Input identity: a private, authorized copy of the 1.09 executable with SHA-256 941f887a562aae054fac35af8cc8f27cf075f3d4cc2e029fb5ae2a663aaa5ae7, plus a record of the loader's second-read identity. A missing or wrong file must give skip 77 and no frames. Eligibility and environment: Linux x86-64 AVX/SysV, UNIX target, default GS, fixed 0x400000 base with no relocation, checked TLS and FP setup receipts, and the 20 pinned source blobs. Phase observations: identity pass, loader success, entry and body guard accepted, math bindings present, a validated positive camera count with the actual step count, nonzero mouse-turn, held, and Original-tuning counters, and final exit 0. Source-faithful positive: a reached collision frame with finite outputs, identical camera words, identical GSM, and equal cast and debug records, where every gate should pass. A payload-only NaN change in a camera word should also pass, and should be labelled as the intended relation. Contradictory raw-field negative: flip one bit in the first 0x20 GSM bytes, such as the Case B slot, on an otherwise identical frame. The frame must fail, the final exit must be 1, and a later agreeing frame must not clear it. For the override control, the pre-arm +0x14 value must be non-sentinel, and the original arm must show -1 after consumption. An input that is already -1 cannot discriminate.

Next action: a real consumer must authorize the executable and environment. Precise blocker: no authorized private copy of the 1.09 image and no environment record was supplied.

## Question 4: Configuration-specific completion and a weak deployment identity

State 0 in both cases. In Case A (mode 2, comparison allocation succeeded), run_prep ran inline on the caller and returned. That return ends the CPU reads. The prep is never submitted to PrepPool, so its state stays at the initial 0 and carries no completion meaning. A pool receipt does not apply to an inline call. Remaining obligations are the GPU reads of the imported guest source, which are recorded passes that close only at the fence of the submission that contains them, and the original allocation owner's rule. The batch wait does not apply because the upload is not in g_batch_preps. In Case B (mode 2, comparison allocation failed), cpu_copy stays empty and the hash-only job is queued, with sf.prep holding it. State 0 there means queued and not yet claimed, so the reads are not complete. The obligations are that job's state 2 or a completed wait on the same prep, the GPU import reads on the GPU branch, and the owner's rule ([route table](https://github.com/Parm-1/Bloodborne-Research-Commons/blob/4dcb72ff2531d116fec68986eff03fb75150cca3/docs/CONTINUATION.md#texture-upload-readers-that-overlap); [textures.cpp 1115-1129](https://github.com/droogie/bbhost/blob/566184a74f071166299bb656c4af479e5bbe2771/src/host/textures.cpp#L1115-L1129)).

Neither the batch submission wait nor mode 2 alone establishes that every reader has finished. The batch wait covers only the async CPU preps in g_batch_preps, which neither case has. Mode 2 is a configuration choice that adds the comparison copy and keeps the GPU branch. Supported statement: Case A has finished its CPU reads and still needs the GPU fence. Case B has finished neither. Both still need the original owner's rule before any release claim.

Deployment description. "r2-development, textures.cpp identical to the research copy" applies only in part. Commit identity needs the resolved commit or tree of r2-development and of the research copy. Minimal records before a target-specific conclusion: the resolved commit or tree; a blob comparison of the 13 dossier source paths against the pin, plus CMake and any other named path; the actual startup environment (BBHOST_GPU_UNTILE, BBHOST_UNTILE_VRAM, BBHOST_TEX_ASYNC, and the TLS settings, with unset values recorded); and a caller comparison for upload_surface and the kernel removal path.
