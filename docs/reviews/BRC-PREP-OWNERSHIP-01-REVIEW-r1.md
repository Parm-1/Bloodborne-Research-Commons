## Decisive source checks

Every source reference below binds the upstream commit above. Line references identify source reasoning, not executed observations.

1. **Actual readers, raw fields and completion.** `textures.cpp:823–875` stores raw `src/base/total_src`, captures layout, and reads untile source followed by sampled/whole hash and exact whole-span hash. Hash-only reads both hashes without untile. `634–676` contains raw host reads with no lifetime check: exact reads the full span; nonexact samples above 256 KiB. Unsupported untile zero-fills destination but still hashes guest memory. The exact hash is the last guest read in these `run_prep` paths. Object ownership is not allocation ownership.

2. **Pool worker/waiter positives and contradictory state.** In `877–940`, queue and worker retain shared pointers; the mutex serializes state-0 claims. A waiter either runs state 0 through `run_prep` and publishes state 2, or waits for state 1 to become 2. A worker skips an entry already claimed by a waiter. These are source-faithful normal completion positives. `1051–1151` also calls nonqueued inline `run_prep` and consumes its hashes while state remains 0; thus treating every state 0 as incomplete would be false. Mode-2 successful CPU comparison is inline; failed comparison allocation can instead submit hash-only work.

3. **Route-specific consumption and erase/reset.** CPU async insertion into `g_batch_preps` occurs at `1141–1143`; hash-only submission at `1133–1135` does not insert there. `3344–3351` waits the CPU batch before retirement/sweeps; `gpu.cpp:5197–5245` performs that wait before handing off/submitting the recording. `settle_prep` at `968–977` waits before copying hashes. In contrast, upload resets the old pointer before mapping/staging checks; the dirty-watch branch at `1712–1760` uploads without settling, while the later hash branch at `1802–1813` first rejects an unfinished prep. Descriptor replacement at `2445–2480`, due retirement at `3295–3342`, and erase bodies at `3389–3505` defer host objects and erase records without canceling/joining the old prep. Queue/worker ownership remains; CPU jobs additionally retain batch ownership. A successful GPU fence and Surface erasure cannot substitute for observing this old hash-only prep's completion.

4. **Allocation/removal, identity and external barrier candidates.** `kernel.cpp:327–440` cuts map records, notifies watch/GX state under the map mutex, then host-unmaps outside it; direct release at `1017–1052` removes physical allocation accounting and unmaps victims without prep joining. Mapping snapshots at `719–800` and watch arming at `479–500` end their lock scope before prep reads; mapped coverage is not CPU readability, original physical identity or retained ownership. Exact mapping at `918–983` changes host mapping before record replacement. Independently checked `dmem_alloc_locked/dmem_release_locked` at `119–175` and `hle_alloc_direct` at `883–904`: released accounting can become allocator space again, with no prep completion condition in these bodies. This is a conditional adapter-level observation, not proof of an original-game overlapping call.

   GX destructor adapters at `gx_resources.cpp:504–538`, unregister/retirement at `369–415`, and memory-release notification at `859–880` do not join prep or delay the kernel unmap. 5. **GPU reads, backing versus suballocation, failures.** `gpu_untile_plan` at `textures.cpp:1010–1047`, push/dispatch at `gpu_untile.cpp:65–72` and GLSL source read at `shaders/untile.comp:94–101` establish recorded addresses and intended read endpoints, not compiled-shader/driver equivalence.
