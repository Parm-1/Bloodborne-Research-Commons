## Batched actionable findings

### F1 — cached coverage does not acquire the runtime read lock

Location: `claims/RC-0020-memory-mapping.md:5`, the sentence saying that non-reserved VMA coverage or direct_phys gives a current lookup under the runtime read lock. Related explanation: `knowledge/guest-memory-mapping.md:28`.

The direct translator takes and releases the read lock, but coverage helpers can return from a generation-checked per-thread cache before acquiring it. [runtime_memory.c:966–974](https://github.com/deadinside28/bloodborne_pc/blob/3c57da4198ad62039f63f33bfd205b9916518acf/src/runtime_memory.c#L966-L974) loads the generation and selects cached fields; [is_mapped:1027–1033](https://github.com/deadinside28/bloodborne_pc/blob/3c57da4198ad62039f63f33bfd205b9916518acf/src/runtime_memory.c#L1027-L1033) returns 1 on that path before read_lock. Clamp and region likewise have cache fast paths at 984–1000. The shim [CachedMapped:130–146](https://github.com/deadinside28/bloodborne_pc/blob/3c57da4198ad62039f63f33bfd205b9916518acf/gpu/shim/bbgpu.cpp#L130-L146) has its own generation cache. A source-faithful positive is an even matching generation with a cached non-reserved region containing the requested bounded span: coverage returns without locking. An odd or unequal generation defeats that fast path; the runtime fallback then locks. [direct_phys:885–894](https://github.com/deadinside28/bloodborne_pc/blob/3c57da4198ad62039f63f33bfd205b9916518acf/src/runtime_memory.c#L885-L894) remains a locked lookup.

This is a demonstrated mismatch in the claim's observation mechanism, not missing runtime evidence. The candidate correctly rejects retained leases and stable bytes, but that exclusion does not make its read-lock assertion accurate. Repair condition: distinguish locked fresh table/direct translation lookups from generation-qualified cached coverage, preserving the absence of a retained reference and writer/content-version guarantees. Recheck only this claim and the affected locking/cache prose against these branches.

### F2 — release can fail to progress after an unmap failure

Locations: `knowledge/guest-memory-mapping.md:30` and contrary case 8 at line 73; the broad batch/release ordering summary in `claims/RC-0020-memory-mapping.md:5` should remain conditional on reaching unlock/flush.

The dossier notices that release ignores unmap_locked's result, but its failed-unmap contrary case groups that outcome with zeroing failure and discusses a result of 0 without identifying the release loop's actual failure path. [unmap_locked:448–453](https://github.com/deadinside28/bloodborne_pc/blob/3c57da4198ad62039f63f33bfd205b9916518acf/src/runtime_memory.c#L448-L453) returns INVALID on munmap failure before dropping the VMA records. [direct_release:472–480](https://github.com/deadinside28/bloodborne_pc/blob/3c57da4198ad62039f63f33bfd205b9916518acf/src/runtime_memory.c#L472-L480) ignores that error, resets i to vma_index of the same original virtual start, and continues. For a still-overlapping VMA and a failing munmap, the next iteration selects that unchanged record again. With a stable installed UNMAP hook, each attempt queues more notifications until [queue_hook:244–248](https://github.com/deadinside28/bloodborne_pc/blob/3c57da4198ad62039f63f33bfd205b9916518acf/src/runtime_memory.c#L244-L248) exits(21) at the 64-entry limit. With no hook, a persistent failure can repeat indefinitely. Neither branch reaches block edits, zero_phys, unlock, hook flush or the return of 0. A later successful retry is a different conditional schedule. By contrast, an ignored hole-punch failure in zero_phys can still precede the normal return of 0.

This is a demonstrated static failure-path omission in the worked contrary case, not a demand for execution or a claim that it occurs on a game target. Repair condition: separate failed-unmap progress/overflow/nontermination from ignored zeroing failures and make post-release phases conditional on reaching them. Keep the successful alias-removal positive and attempted-zero limit. Recheck the release loop, queue interaction and affected summary/row; no unrelated runtime investigation is needed.
