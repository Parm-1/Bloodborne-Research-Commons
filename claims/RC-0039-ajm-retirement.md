In a defined, externally ordered public-producer schedule, successful wait clears an occupied global batch slot after checking that the supplied context is currently live; it never compares the slot's stored context. Successful cancel validates that same condition and mutates nothing. These returns do not undo synchronous writes, inspect per-job results, prove original batch/context allocation identity or establish sink/audible completion.

**Primary:** [src/runtime_ajm.c:367–388](https://github.com/deadinside28/bloodborne_pc/blob/3c57da4198ad62039f63f33bfd205b9916518acf/src/runtime_ajm.c#L367-L388), [426–477](https://github.com/deadinside28/bloodborne_pc/blob/3c57da4198ad62039f63f33bfd205b9916518acf/src/runtime_ajm.c#L426-L477), blob `9d69d25112ebbfcdc6db3a920b14664a96f7593d`. **Meaningful negatives:** an empty batch publishes without jobs; wait ignores timeout/error and repeated wait without reuse fails. A second live context can retire the first context's slot. Reused batch numbers let a stale wait retire a newer slot. Finalize frees context/handles but leaves batch slots occupied; after numeric context recreation an old slot can be retired. No public path sets canceled1, so the present cancel does not produce a cancelled-wait branch. Instance high bits are not a generation/live codec check. Counters/trace and unlocked context reads are separate concurrency limits, not blanket thread-safety evidence.
