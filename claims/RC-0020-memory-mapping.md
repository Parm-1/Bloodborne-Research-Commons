# RC-0020 — Linux mapping coverage and physical backing are scoped observations

**Level:** SOURCE_INSPECTED, 2026-10-13; public bbport `3c57da4198ad62039f63f33bfd205b9916518acf`, selected Linux source. Proposed BRC-MEMORY-MAPPING-01 / Batch 02 Issue #16 item 1. Independent review and acceptance pending. No runtime, native fixture, device or game observation.

At the exact bbport pin, direct allocation, virtual mapping, stored protection, shared physical backing and queued cache notification are separate operations. Fresh direct_phys and table-query fallbacks use the runtime read-lock helper, while is_mapped/clamp/region and shim CachedMapped can return from generation-qualified caches before acquiring it. An observed even matching generation plus the applicable range/kind predicates supports that cached return; odd or mismatched runtime generations defeat that runtime fast path. The shim returns false for an odd generation; with an even mismatched shim generation it calls region, which can hit the separate runtime cache. Neither path retains a lifetime reference or stable byte version. Successful aliases of the same established physical backing share storage; covered adjacent VMAs need not be physically contiguous. Standalone unmap notifies before mutation; batch flushes after unlock, and release reaches its later block edits, attempted zeroing, unlock and flush only if its alias loop finishes. Persistent munmap failure leaves the selected VMA unchanged: release retries it, reaching queue overflow exit(21) with a stable UNMAP hook or repeating indefinitely with no hook. This does not return 0. Ignored hole-punch failure after successful alias removal is a separate path that can return 0. Partial failures have no general rollback guarantee.
