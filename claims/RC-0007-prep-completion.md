# RC-0007 — CPU batch submission wait does not include GPU hash-only prep

**Level:** SOURCE_INSPECTED. **Subject:** bbhost `566184a74f071166299bb656c4af479e5bbe2771`, texture preparation and Vulkan submission. **Checked:** 2026-10-12. **Independent review:** uninvolved Sol/high `prep_ownership_review`, [r1 source review](../docs/reviews/BRC-PREP-OWNERSHIP-01-REVIEW-r1.md), no actionable finding; parent accepted source/documentation scope. R2 integrates status/report only; technical body unchanged. The [public r2 fresh-reader check](../docs/reviews/BRC-PREP-OWNERSHIP-01-FRESH-READER-r1.md) completed with a precision finding; r3 repairs post-erase observability wording, pending the same reviewer's affected recheck.

CPU async upload adds its shared prep to `g_batch_preps`; submission waits every entry to pool state 2 before GPU consumption. GPU-route hash-only upload submits to the same pool and attaches to Surface but does not add to that batch. Its guest hashes complete when that prep's `run_prep` ends and state 2 is published, or a wait on that same prep finishes. Observing this requires the same job reference: the inspected producer/reset/erase and submission/retirement interfaces expose no post-erase receipt for the old hash-only job once its Surface reference is gone. Queue/worker ownership does not expose a caller handle, and a new prep at the same base is not that job. A GPU submission/fence alone is not that completion.

**Source/method:** read complete producer, pool/wait and consumption bodies: [upload](https://github.com/droogie/bbhost/blob/566184a74f071166299bb656c4af479e5bbe2771/src/host/textures.cpp#L1101-L1151), [pool/read/settle](https://github.com/droogie/bbhost/blob/566184a74f071166299bb656c4af479e5bbe2771/src/host/textures.cpp#L823-L976), [batch](https://github.com/droogie/bbhost/blob/566184a74f071166299bb656c4af479e5bbe2771/src/host/textures.cpp#L3344-L3351), [submit](https://github.com/droogie/bbhost/blob/566184a74f071166299bb656c4af479e5bbe2771/src/host/gpu.cpp#L5197-L5227), [submission/retirement declarations](https://github.com/droogie/bbhost/blob/566184a74f071166299bb656c4af479e5bbe2771/src/host/gpu_internal.h#L1284-L1300).

**Meaningful negative:** hash-only state 0/1 with Surface erased after GPU submit is not changed to state 2 by erase; queue/worker still owns the prep. A CPU waiter may run state 0 itself or join state 1; normal wait returns only after reads. Nonqueued inline CPU prep finishes before return despite state remaining 0. Even the same job's completion would not prove its original allocation stayed valid during the reads. These are source deductions, not executed cases.

**Exclusions/unknowns:** raw guest allocation retention, permitted writer/version interval, game reachability, all shutdown paths and GPU driver behavior. **Reuse/ownership:** KNOWLEDGE_REFERENCE; droogie/bbhost, declared GPL-3.0-or-later in [registry](../sources/projects.yaml); no code imported. **History:** new atomic r1 finding; r3 adds the fresh-reader observability qualification without changing the lifetime/writer UNKNOWN.
