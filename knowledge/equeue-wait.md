## Small-timer, VideoOut and callback applicability

This is the narrow exception to the normal user-event wait path, not a timer-accuracy study. Public AddHRTimer checks queue then reads `ts`, computes total ns and bintime. For defined safe values below1200000ns it calls AddSmallTimer, which copies the raw event and stores an interval in a separate id-keyed map. For safe `ts={0,0}`, that path has zero interval without conversion/overflow ambiguity. Nonzero waits that select HasSmallTimer bypass m_events and use WaitForSmallTimer's steady-clock scan/yield loop; it returns only expired small timers (up to num), erases them and returns immediately when any copied, or0 at its own finite deadline. It does not use m_cond or react by scanning User after a wake. A null timeout gives maximum end time there; adding/removing timers around branch selection changes applicability. Zero-timeout poll occurs first and sees m_events only. Small-timer copies are not normalized by AddEvent; do not transfer user flags/data/count meaning or an exact duration guarantee to them. See cpp263–311,540–589 and h144–179. The [clock study](clock-sleep.md) supplies only its own qualified domains, not this branch's runtime accuracy.

For scheduled timers, cpp126–164 captures raw `this` and copied event in async_wait. Its error branch returns before dereferencing m_handle; a success branch reads `this->m_handle` and calls the callback. Timer/HrTimer callbacks look up raw registry pointers; the regular timer additionally checks EventExists then triggers/reschedules in separate steps. DeleteUser does not own such a timer. Erasing a timer-bearing record/queue destroys its unique_ptr timer, but this is not a callback join. Named Boost1.85 destructor/cancel descriptions say outstanding waits are cancelled; the cancel description expressly allows already-expired successful handlers already invoked/queued, and async_wait dispatch is separate from initiation. This is a conditional dependency/lifetime concern: a success handler with stale `this`, or registry/key reuse between callback steps, lacks a local lease. No actual callback schedule, cancellation error-code equivalence, installed Boost identity or observed use-after-free is claimed. bbgpu's kernel service runs io_context on its jthread; queue deletion never stops or joins that service. No service scheduler or all-timer audit is supplied.

VideoOut public registration uses the same queue/key machinery with filter−13; AddEvent adds Clear for that filter. Driver flip/vblank paths look up queue and trigger a VideoOut record. A queue can therefore contain other filters, and WaitForEvents does not filter output by the caller's last User trigger. The incorporated [VideoOut dossier](videoout-flip.md) owns packing, presentation and lifecycle semantics; this study reuses it as a scoped reference, not independent corroboration. Its trigger precedes previous-label clearing in the inspected flip path, so a wake cannot promote label reset or external work completion. Do not interpret User data0 using VideoOut packed count, or apply User udata overwrite rules to other filters.
