Consumer: runtime/thread maintainer deciding what key create/set/get/delete/reuse and selected guest-thread cleanup establish about a stored pointer, callback completion and retirement. **Treat the key as a reusable numeric slot, the value as a calling-host-thread pointer association, and a returning cleanup as completion of its selected synchronous calls only.** Neither deletion nor cleanup owns the pointed-to allocation, proves its content identity, drains work started by a callback or establishes a generation. Four scan rounds do not guarantee callback termination or bound cleanup restarted by guest exit.

## Producer, observation phase and identity

Here `kernel`, `thread` and `runtime` refer to the pinned bodies above. All conclusions require defined access, valid types/storage and an ordered schedule.

| Phase / source | Conditional contract | Discriminating limit |

| Registration — [kernel245–260][kernel] | Global `keys[256]` stores ordinary `int used` and `KeyDestructor`; one mutex serializes create/delete registry writes. Create takes the lowest unused index1..255, marks used, stores D, unlocks, then writes a uint32 key to caller output. Null output gives raw `0x80020016`; exhausted slots give `0x80020023` (guest35). | Capacity is255 simultaneous registrations; index0 is reserved. There is no generation, reset of any `key_values`, payload allocation/copy or destructor invocation. A nonnull output must be valid aligned writable uint32 storage. Lock results and arbitrary nonnull pointer validity are unchecked. Output publication occurs after unlock and needs caller ordering before other consumers. |
| Set/get — [kernel269–273][kernel] | Set rejects0, ≥256 or unused with raw `0x80020016`; otherwise stores exactly the supplied void pointer in the calling host thread's `_Thread_local` array. Get checks only1..255 and returns that thread's stored pointer; invalid range returns null. | Get never checks `used`. Null can mean unset, explicitly null or invalid range, and proves neither registration nor cleanup. Replacing a value calls no destructor. | Delete/recreate — [kernel250–268][kernel] | In-range delete locks, returns0 if used else raw22, then clears used/destructor in either case. It never writes thread values or calls D. Next create can reuse the lowest free slot and install another destructor. | Ordered get after deletion may still return a live old P although set rejects that key. | Cleanup selection — [kernel274–285][kernel] | Each invocation scans1..255 in ascending order for up to four rounds. Callback code and payload must stay valid through the actual call. Delete is not a barrier against active callbacks. |
| Returning callback and later selections — same bounds | Own-slot get inside D sees null unless it or earlier callback activity repopulated it. Callback key delete/recreate changes subsequent selection, under defined same-thread ordering. | Four rounds bound direct calls per uninterrupted invocation, at most4×255, only if each call returns and the invocation is not abandoned/reentered. | Entry/exit and cleanup tail — [thread220–227,279–285][thread] | Actual `host_start` attaches, establishes its checkpoint, stores ordinary entry result or accepts guest-exit result, calls cleanup, then marks finished and returns. No key payload free, descendant drain, guest-record/TLS/stack reclamation or callback-code unload protocol is established. |

Errors above describe uint32 raw bit patterns under the intended int32 return representation/ABI. POSIX adapters [kernel286–288,310–313][kernel] return0 or `r&0xffff`, yielding22 or35 directly, without `fail_posix`/guest errno writes. Getspecific shares the pointer-returning body. This is guest35, not proof of the host's numeric EAGAIN. Arbitrary invalid nonnull output, invalid callback, expired pointer values or failed mutex operations have no promised recoverable error here. Windows resolves none of these kernel exports and its cleanup body is empty; Linux conclusions are not Windows qualification.

Create/delete use the mutex but set and cleanup read plain registry fields without acquiring it. A concurrent conflicting writer without a demonstrated happens-before relation invalidates the defined-C premise; no deterministic old/new/mixed destructor, crash or return is predicted. The TLS array prevents ordinary cross-host value-slot sharing; it does not synchronize the pointed-to object or the global registry. Externally ordered quiescent transitions and same-thread callbacks give useful defined counterexamples without inducing races.
