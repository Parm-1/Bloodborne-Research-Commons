Whole-tree selected API direct-call/name/NID searches find only definitions and registrations; no direct public HR add/delete caller or selected import-table metadata was found. Indirect, generated and guest calls remain UNKNOWN. No fabricated caller, serialized record or native fixture is supplied.

Use a live, stable, correctly typed queue; valid suitably aligned readable `ts` stable throughout add; distinct adequately backed writable `ev[capacity]` and `out`; positive int capacity; and a stable readable u32 timeout when non-null. Assume compatible Linux x86-64 LP64 arithmetic/ABI, successful ordinary allocations/dependencies, representable duration/time-point arithmetic and conversions, and actual ordering of conflicting accesses. Pointer-to-u64 conversion must preserve the implementation's local address round trip used synchronously by add. A declaration/non-null pointer alone proves none of these premises. Keep registry mutation/deletion, timer callbacks, re-adds, polling and output readers ordered as each case specifies; internal map locks do not serialize every registry or poll operation. No undefined race outcome is predicted.

Queue handles are s64 at the public boundary but the registry key is s32. Within the cited C++23 conversion description, q and q+2^32 select the same normalized key, assuming representable supplied inputs. Public int IDs become u64; nonnegative IDs are used except H3's explicit -1 conversion. Vector key is `(ident,filter)`; the small map key is ident alone. Neither storage carries a generation token. Opaque udata is copied numerically; its pointed-to object's lifetime and any external work protocol remain caller responsibilities.
