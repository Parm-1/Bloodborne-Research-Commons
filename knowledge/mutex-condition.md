## Storage, configuration and callable intake

[Producer:11–80](https://github.com/deadinside28/bloodborne_pc/blob/3c57da4198ad62039f63f33bfd205b9916518acf/src/runtime_mutex.c#L11-L80): caller-owned writable handle slots contain pointers to separately allocated `GuestAttr`, `GuestMutex` or `GuestCond`. Native pthread objects live inside the latter allocations. These are not semaphore uint32 IDs. Copying the pointer creates an alias to the same allocation, not a new mutex/condition or retained lifetime. Slot validity, pointed allocation, native initialization and lock ownership are four different premises. Numeric pointer range checks do not establish any of them.

`GuestAttr` contains only `int type`. Init sets1; setter accepts1..4. On mutex creation, type2 selects RECURSIVE, type3 NORMAL, type1/4 ERRORCHECK. This is an explicit translation, not a cast of host enum values. Init applies only type, checks native attr-init/settype/mutex-init results, ignores native attr-destroy result, then publishes via plain `*out` and increments `created`. Later attribute mutation/destruction does not reconfigure that mutex. Name is ignored. The protocol setter accepts0..2 and returns0 but stores nothing and calls no host protocol/scheduler setter; the comment's claim that it is recorded is contradicted by the struct and function. There is no PS4 scheduling or priority-inheritance qualification.

Mutex lock/try/timedlock use `ensure_mutex`: an acquire load rejects2, accepts values greater than2, and lazily creates default type1 for0/1 under the global `static_init` mutex with release publication. The second check and downstream accesses are plain. The comment about once-only initialization under contention is not a complete C concurrency proof. `ensure_cond` has the analogous0/1 path but accepts **all values >=2**, including2; it does not share the mutex tombstone rule. Condition init ignores the supplied attr/name and calls `pthread_cond_init(...,NULL)`, using host defaults, not the requested condition attribute.

[Intake/adapters:200–254](https://github.com/deadinside28/bloodborne_pc/blob/3c57da4198ad62039f63f33bfd205b9916518acf/src/runtime_mutex.c#L200-L254): exact scoped strings select SysV-annotated wrappers. ## Operations and observation phases

[Lock/unlock:81–130](https://github.com/deadinside28/bloodborne_pc/blob/3c57da4198ad62039f63f33bfd205b9916518acf/src/runtime_mutex.c#L81-L130): lock first tries the native mutex. Only EBUSY enters blocking lock and records wait kind1 afterward. Other results are mapped directly. Trylock is one native attempt; timedlock constructs a realtime deadline then invokes native timedlock. A host success maps0 and increments `locks`. Under the separately stated host contract, a valid non-robust successful lock belongs to that calling thread; a successful recursive relock increments depth. Unlock checks null/tombstone, gives EPERM for raw0/1, then calls native unlock and increments `unlocks` only on host0. Recursive unlock0 can decrement depth without releasing the mutex. Wrong-owner NORMAL unlock is outside a defined positive; ERRORCHECK/RECURSIVE host errors map when supplied by the host. This wrapper stores no owner/depth field and cannot infer ownership from a pointer or global counts.

[Condition operations:132–205](https://github.com/deadinside28/bloodborne_pc/blob/3c57da4198ad62039f63f33bfd205b9916518acf/src/runtime_mutex.c#L132-L205): wait ensures the condition first, then rejects null mutex slot or mutex raw<3. It **does not** ensure/init/lock the mutex. A lazy condition can therefore be created even when subsequent mutex validation fails. At the host wait boundary, the caller must already own a live valid mutex with the applicable condition binding. The producer increments `waits` before the native call; after native return it records kind0 duration then maps the result. It maintains no Boolean predicate, waiter registry, notification credit or recursive-depth repair. Signal/broadcast ensure the condition, increment `wakeups` before the native call and map its result; they do not inspect a predicate or join a waiter.

For valid ordinary host waits, the separately cited API describes release while waiting and reacquisition on success or timeout. A successful return still requires caller predicate recheck; a timeout can race with a true predicate. An early validation/error return is not evidence of release/reacquisition. Different mutexes for concurrently blocked waits on one condition violate the API's dynamic binding requirement. Recursive depth>1 must not be promoted to a full mutex release: the type API explicitly cautions that implicit unlock may leave it held. Signal with no current waiter is not saved for a later wait. Broadcast unblocks current waiters; mutex contention/return endpoints remain separate, with no FIFO/priority or progress promise from this wrapper. External cancellation can prevent normal wrapper return; this package excludes cancellation/nonlocal exit rather than asserting cleanup safety.

## Deadlines, result domains and diagnostic limits

[Deadline/error producer:14–27, 115–130, 175–220](https://github.com/deadinside28/bloodborne_pc/blob/3c57da4198ad62039f63f33bfd205b9916518acf/src/runtime_mutex.c#L115-L130): SCE timedlock/timedwait take a by-value uint32 microsecond interval, not an in/out remainder or absolute timespec. `deadline_after` reads CLOCK_REALTIME, normalizes nanosecond carry, adds seconds via `time_t`; failure is flattened to guest EINVAL. Mutex admission occurs before this read; SCE condition admission occurs after it. `usec=0` still calls the native timed operation if setup succeeds. Maximum input is4294967295 microseconds. Deadline construction precedes native waiting; admission/descheduling can consume that interval, and wall-clock jumps can affect its absolute expiry. There is no minimum/maximum observed elapsed-time guarantee. Native timedlock's API permits immediate acquisition even for an expired deadline.

POSIX timedwait instead reads `GuestTimespec {int64_t sec,nsec}` through a pointer, rejects null or nsec outside0..999999999, casts to native `time_t`/`long`, then calls the same absolute wait helper. Source does not validate seconds representability or negativity. The comment that its layout is identical to Linux x86-64 is not installed ABI proof; native sizes/alignment and casts require independent qualification. Neither timed API writes the input interval/timespec. Defined arithmetic examples require representable conversions/addition and valid successful clock samples. Diagnostic `runtime_wait_clock` instead uses CLOCK_MONOTONIC, ignores clock_gettime's result and can read uninitialized `t` on failure; its duration is not the realtime timeout authority.

SCE results are int32 values formed from raw32 `0x80020000|code`: EPERM1, ENOMEM12, EBUSY16, EINVAL22, EAGAIN35, EDEADLK11; timed helper additionally maps ETIMEDOUT to `0x8002003c`. The POSIX adapter returns the low16 bits as a positive guest errno: respectively1/12/16/22/35/11/60, not Linux's numeric errno table, `-1` or a proved original SDK enum. Unmapped host errors print STOP and exit21; they do not produce a guest return. Robust owner-death recovery is not configured, and no outcome is inferred for a foreign robust object. Lazy helper native lock/unlock results and native attr-destroy result are ignored. A failed ignored operation defeats assumptions about publication/ordering even if a later wrapper value is0.

The global plain size_t counters (`created/locks/unlocks/conds/waits/wakeups`) are attempted-path diagnostics, not live ownership/depth or object counts. `waits` includes a native call that returns an error; `wakeups` counts signal/broadcast attempts even with no waiter or host error; neither counts returned waits. Report reads have no common synchronization. Native mutex protection does not order every global counter across different objects; `unlocks` increments after native release. Wait-note also has plain initialization/metadata accesses despite atomic aggregate fields. Concurrent conflicting updates/reads cannot be treated as defined C positives or fixed by interpreting their numbers. Broad concurrent lazy publication and diagnostics remain unqualified.

Every positive below assumes valid, correctly aligned/typed slot and attribute/native storage; compatible pointer/uintptr/compiler extension and SysV calling conventions; no stale aliases, destruction or reinit during use; successful relevant ignored host calls and clocks; representable arithmetic; no cancellation/fault/nonlocal exit; and no C data races, including diagnostics. Single-thread rows satisfy only their own sequencing premises. Multithread reasoning additionally requires established diagnostic initialization and externally ordered conflicting updates/report reads; this source study supplies no such execution receipt. Thus host branch implications are conditional, not a demonstrated race-free implementation of all schedules.

## Retirement and reconstruction

[Destroy:108–113, 158–163](https://github.com/deadinside28/bloodborne_pc/blob/3c57da4198ad62039f63f33bfd205b9916518acf/src/runtime_mutex.c#L108-L113): mutex null-slot/tombstone yields EINVAL; raw0/1 destroy returns0 without allocating or changing the slot. A live native destroy0 frees the allocation and writes2; native error leaves it intact. Condition null-slot yields EINVAL; raw0/1 destroy returns0 unchanged; live native destroy0 frees and writesNULL, error retains it. Native destroy preconditions must already hold. Locked/in-use mutex or blocked condition destruction is not a portable EBUSY test; the API declares invalid uses undefined, and the public test's EBUSY assertion is not proof otherwise.

Neither operation waits for arbitrary caller work or revokes copied handles. The selected APIs contain no retain/refcount/generation check. After successful destruction, only the passed slot changes; another slot holding the freed pointer is dangling. Explicit mutex/condition init allocates a fresh native object without checking the old output value, so it can replace2/NULL after safe retirement; overwriting a still-live pointer instead loses that reference and can leak the old object. Lazy lock of mutex2 rejects; condition signal after destroyNULL can lazily allocate a new default condition and succeed without any waiter. Equal reused addresses are not generation identity. None proves a former caller/thread has terminated.
