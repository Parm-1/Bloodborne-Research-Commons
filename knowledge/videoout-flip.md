# Ordinary VideoOut CPU flip: admission, rendering and presentation

**Proposed SOURCE_INSPECTED — 2026-10-16.** BRC-VIDEOOUT-FLIP-01 / [Issue #24](https://github.com/Parm-1/Bloodborne-Research-Commons/issues/24). Consumer: presentation maintainer deciding whether ordinary CPU submit/status/event/label permits queued-work accounting, interpreting covered rendering completion, buffer reuse, or physical presentation. Independent review, root acceptance and human editorial acceptance/merge are pending. [RC-0040](../claims/RC-0040-videoout-admission.md), [RC-0041](../claims/RC-0041-videoout-completion.md), [frontier](../frontiers/videoout-flip.md), [author r1](../docs/reviews/BRC-VIDEOOUT-FLIP-01-AUTHOR-r1.md). The four preceding semaphore, mutex, clock and AJM proposals are reviewed/root conditionally accepted but open/unmerged integration predecessors; this study does not change their technical bodies or accept them into main.

A successful ordinary CPU submit admits work to a command queue. The implementation's flip status/event/previous-label update follows scheduling of presentation work; under default separate-swap configuration it can precede execution of that work. Neither observation is a physical-display receipt. The optional honest-flip wait is useful only when its exact frame/timeline identity stays stable and the actual wait succeeds; its return alone is insufficient. No source, GPU, device, fixture, UI or game execution occurred here.

## Raw fields and timing premises

`FlipStatus` has u64 count/process_time/tsc/submit_tsc, s64 flip_arg, signed32 pending/gc/current index; its declared defaults include current−1, arg−1, pending0. The API copies it under port_mutex. Close resets under a different mutex and event/label/config accesses are not a comprehensive synchronized snapshot; exclude overlapping lifecycle mutation rather than claiming race safety. A status count increment can precede old-label reset; pending0 may coexist with swap callbacks or GPU work. Conversely pending can reflect accepted work not yet in the Request queue. The pending counter is aggregate CPU+EOP, not queue size and not a per-buffer version.

The pinned C++23 build matters for `(req.flip_arg <<16)`: N4950 gives modulo-width shift semantics for a valid shift count; negative left input is not the old C11 undefined-shift case. Upper16 argument bits are discarded by the64-bit shift. Event transport additionally requires a qualified integer↔pointer mapping; its representation and bit-field layout are implementation premises, absent here. `TriggerDisplay` bit_casts stored event.data to its 12/4/48-bit aggregate to read the old count, but static_casts the entire hint integer into a different aggregate whose first field is only8 bits. For out-of-range first-field values that conversion's result is implementation-defined; low8 truncation must be established separately. Arg0 produces raw hint6 and avoids that narrowing in the flip-ID comparison. These are conditional calculations, not an installed ABI result.

Under explicit low-field-first bit layout, 64-bit integer/pointer round-trip and low8 truncation premises, one trigger writes `(TSC &4095) | (min(previous_count+1,15)<<12) | (arg_low48<<16)`. Repeated unread triggers coalesce, saturate count15 and retain the latest argument. Retrieval copies the one triggered record and clears its data/count when Clear is set (AddEvent sets Clear). It is not one queued record per flip. `GetEventData` shifts **u64** data right16 and takes its `data>=0` branch for every raw value: result is unsigned low48 argument widened to s64, including for a negative original arg. `GetEventCount` uses aggregate static_cast, initializing the first time field from the entire raw integer and value-initializing count/arg to0; it does not bit_cast/extract the packed count. Thus a correctly stored raw count and a returned count0 are compatible. First-field narrowing affects time's value, not the zero-initialized count. No original SDK event compatibility is established.

Settings are premises, not hardware measurements: `BB_VBLANK_HZ` defaults60, nonpositive→480 and raw>120/nonpositive selects uncapped; `BB_FPS_LIMIT` defaults0 and clamps negative parsed values to0; positive large/narrowed values still require safe admitted bounds, nonzero frequency and meaningful periods. PresentThread takes integer nanosecond periods once, gates using software count modulo(rate+1), and emits vblank events with **pre-increment** software count before status count increments. `BB_PRESENT_MODE` requests Mailbox by default, with supported-mode check/Fifo fallback; it is independent of the software tick/rate gate. `BB_HONEST_FLIPS` is first-use cached; `BB_PRESENT_THREAD` is constructor-read; `BB_FRAMES_AHEAD` is first-use cached. Comments claiming PS4 behavior, game lighting tests, measured timing/performance or hardware-specific improvements remain PROJECT_REPORTED, not reproduced evidence.

EOP is only a contrast: video_out345–359 registers one GfxFlip IRQ callback, asserts the selected label1, then calls SubmitFlip(...,true); it uses direct internal preparation and gc accounting. This is not the ordinary CPU route and not a full command-parser, GNM, interrupt, label-writer or GPU coverage audit. A label1 from that contrast cannot be imported into the ordinary producer's contract.
