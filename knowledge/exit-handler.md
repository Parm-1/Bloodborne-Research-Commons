Consumer: a lifecycle maintainer deciding whether an accepted registration, filtered/global finalizer return or selected guest exit establishes callback completion and permits reclaiming callback code or argument storage. **Track the individual accepted record through selection → inactive mark and local copy → callback start → callback return.** Inactive is a selection state, not a completion state; no code, argument or DSO lifetime lease is acquired.

## Accepted records, identities and retained storage

[Runtime:12–18,108–130][runtime] stores a callback union, argument pointer, DSO pointer, with_arg discriminator and active flag. Plain registration rejects a null callback before incrementing calls_atexit; otherwise it increments that plain size_t counter and supplies a zero-initialized remainder, including null argument/DSO and with_arg0. Cxa registration similarly rejects null, increments calls_cxa and supplies callback/argument/DSO with with_arg1. Null argument and null DSO are accepted with a non-null callback. A registration attempt counter is not an accepted record count.

Under handler_lock, admission grows capacity from 0 to 64, then doubles when count==capacity; proposed capacity above 1048576 produces failure without realloc. A failed allocation/cap returns-1 with count/capacity/old registry unchanged. Successful growth replaces the allocation; acceptance sets active1 and appends one record, increments count, then returns0 after unlocking. Existing spare capacity needs no allocation. This reasoning assumes successful intended pthread lock/unlock semantics, valid allocator results and representable allocation arithmetic on the selected host; their return codes are ignored. No injected allocator or pthread failure was run.

Each success creates a distinct record even for identical callback/argument/DSO values. The function address is not a unique registration ID. The DSO field is compared as a pointer value; it is not inferred from the callback's code address or the argument, dereferenced, resolved as a module, reference counted or mapped-validated. Keep valid stable token values and their identity contract through comparisons; pointer reuse or a different caller's token does not prove the same module generation. Callback code and any pointee the callback needs must remain valid through the last relevant invocation's return, including other finalizers. Registry storage retention supplies no such ownership.

Count and capacity never shrink here; inactive slots are neither reused nor removed, and finalize does not free handlers. With ordinary selected-host arithmetic, at most 1048576 records can ever be accepted by this registry, including already inactive ones. A full inactive registry still rejects another registration. runtime_start changes capability/canary setup, not registry/count/counter reset. This is registry retention, not evidence of a deliberate external resource lease or a complete process-unload protocol.

## Selection, invocation, recursion and return

Each [finalize iteration:131–145][runtime] locks, starts from current count, and scans backward over inactive records and, for a non-null requested DSO, records whose stored DSO differs. A null requested DSO is a wildcard over all active records, including plain/null-DSO records; it cannot mean only null-DSO records. The highest-index eligible active record is copied by value to a local variable and its registry active flag is cleared **before unlocking and before invocation**. With_arg selects the appropriate union member and passes the saved argument only for the argument form. On a normal callback return, the loop locks and rescans from the current end. Registration and filtering are per record, with no function-address deduplication.

The local structure copy does not retain a pointer to the registry slot. A later successful registry realloc can move the array while the callback uses its local callback/argument/DSO/discriminator values; that alone does not invalidate the local record. It does not copy argument contents or pin callback code. N1570's realloc description preserves old contents on failure and moves retained bytes on success; object lifetime/function-call requirements and race rules remain separate host-language premises.

Under valid data-race-free calls and successful mutex operations, the inactive mark makes each accepted record selectable at most once. Repeated or recursive finalize skips that record even while its callback is running or has not begun. It does not guarantee the callback began or returned: cancellation, nonlocal transfer, process termination, a fault or a nonreturning callback can interrupt the selected path. A later registration of the same function is a new active record and can be invoked again.

With one finalizing thread, no recursive finalization, no new registration and normally returning callbacks, invocation and completion follow descending eligible index. With recursive finalization, an outer callback can invoke an older callback before it returns: start order and completion order differ. If callbacks append new eligible records, the next scan selects those ahead of older survivors. A DSO-filtered call leaves newly appended nonmatching/plain records for another filter/global call unless a nested call selects them.

Across concurrent finalizers, the mutex serializes selection/marking, **not callback invocation or completion**. One finalizer can select newest B, unlock and pause before calling B; another selects older A and invokes A first. Or B is already running/inactive and another finalizer finds no active match and returns while B continues. No running count, completion flag, condition variable or join exists in these bodies. These countermodels pre-register all records before starting the finalizers, avoid registration/report races, and assume safe independent callback bodies. They therefore do not depend on undefined counter races. A return only records an empty eligible scan at that lock acquisition; registration immediately after it can make a new eligible record.

The useful completion positive is narrower: with no other in-flight finalizer/callback, valid retained identities, successful locks, no abnormal transfer, every selected callback returning after finite work, and sufficient scheduling progress, a normal outermost finalizer return follows completion of the callbacks it and its synchronous nested calls invoked. It leaves no eligible active record at its final scan. Ineligible records remain. The append cap bounds accepted work, even if callbacks register replacements; it does not make callback code finite, prevent infinite recursion/waits inside a callback, guarantee mutex fairness or promise a wall-clock bound. Callback-generated asynchronous work still needs its own completion observation.

## Counters, selected guest exit and distinct probe paths

[Runtime:18,86–90,121–129][runtime] uses plain size_t registration counters, incremented outside handler_lock. Simultaneous same-counter registrations without external ordering can race even though list changes are locked. Report reads count without that lock and counters without atomics: racing report/registration is not a valid synchronized snapshot. Supply external happens-before ordering or quiescence for these reads and increments; do not assign deterministic lost counts to undefined behavior. Different registration forms write distinct counters but reporting still needs ordering. Finite counters can wrap under repeated failed non-null attempts; null attempts are excluded. Quiescent count is accepted records retained, including inactive/running/completed ones, not pending handlers, completed callbacks, freed resources or successful DSO unload. Calls_init is also plain and outside this study's concurrency contract.

[Guest_libc_exit:198–203][runtime] prints status, calls global finalize, then report, then host exit(status). Reaching the exit call requires both preceding calls to return. It supplies no global callback join, no guest thread join, no independent asynchronous cleanup completion and no universal exit-hook integration. The host C description distinguishes normal termination and host-registered atexit callbacks; these guest records are stored in this private registry, not registered with host atexit by these wrappers. Full host termination, recursive host exit, exceptions, TLS cleanup and module unloading are deferred. Reuse [thread lifecycle](thread-lifecycle.md) and [static guard](static-guard.md) only within their existing scopes; guard publication does not register a destructor here.

[Probe:139,576–589][probe] passes a different guest_exit callback to guest entry; that body only prints its finalizer-callback message and returns. Its message is not a registry-finalization/completion receipt. The unsupported-import trap [probe:115–129][probe] reports, flushes and calls _exit(20), without an explicit runtime_finalize in that route. Neither printed callback text nor a runtime report proves guest_libc_exit ran. These are the selected source paths, not a full inventory of termination routes or observed host behavior.

The comparative [Itanium API §3.3.6](https://itanium-cxx-abi.github.io/cxx-abi/abi.html) describes callback/operand/home-DSO registration, reverse enqueue order, matching/all finalization and preventing duplicate entry calls. It does not establish this implementation's callback completion synchronization or actual console/linker DSO handles. The document explicitly disclaims authoritative ABI status for a particular platform. No original-console equivalence, full C/C++ conformance or dlclose safety follows from similar API names.
