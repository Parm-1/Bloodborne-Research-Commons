C distinguishes thread storage from allocated storage: the former has a separate object for each thread and ends with that thread; ending a pointer object's lifetime does not call free on its pointee. Static/thread aggregates without explicit initializers receive recursively initialized null pointer/zero members. Successful calloc supplies zero-bit storage; memcpy needs valid nonoverlapping accessed extents. Allocation alignment covers fundamental types, not arbitrary module alignment or arbitrary offsets. Pointer addition must stay within the allocated object or its one-past position; dereference additionally needs a valid in-object span/type/alignment/lifetime. Unordered conflicting non-atomic accesses have undefined behavior. GCC describes the annotation's intended System V calling convention on x86. None of these rules proves that this target satisfies those premises.

## Metadata producer and actual setter callers

The direct [setter:52–56][runtime] rejects only module IDs below2 or at least8, with diagnostic/exit21. For IDs2..7 it assigns plain process-global data, filesz and memsz fields separately. It borrows the data pointer; it neither copies bytes, allocates blocks, validates filesz≤memsz, non-null/readable template or size conversion, synchronizes, nor clears existing host-thread blocks. runtime_set_libc_tls is exactly a module2 wrapper. ID is an array slot, with no generation field, module object or unload token.

The selected [multi producer:129–164,192–195,216–223][modules] assigns IDs starting at2 only for modules having a first type7 header; absent TLS uses module0. It requires filesz≤memsz and containment of the full memsz within one selected load segment, then emits seven little-endian unsigned64 fields `(base,size,init,tls_address,tls_memsz,tls_filesz,tls_module)` per module in BBPROBE5. It increments the ID without a shown 2..7 limit at that assignment; selected loader checks later reject unsupported nonzero IDs. Its selected kind16 relocation writes module_id only after checking empty symbol name, type3, zero addend and a TLS module; that word alone is not a validated full two-word descriptor or offset/access-width proof. The corresponding [libc producer:118–132,180–188][libc] selects its first TLS header, validates filesz≤memsz and mapped memsz, fixes module2 in a kind16 word, and emits BBPROBE4 metadata with memsz before filesz. Its adjacent-offset comment is PROJECT_REPORTED intent; actual compiled guest descriptor/call behavior is UNKNOWN. No full ELF/SELF parser, relocation, link completion or image audit is claimed here.

[Probe:403–449][probe] reads these fields using its little-endian read64. BBPROBE5 uses raw module IDs; BBPROBE3/4 installs module2 in its single linked record. For nonzero module IDs the selected checks require ID2..7, tls_address<size, memsz≤size−tls_address, memsz≤1MiB and filesz≤memsz. The later [mapped check:483–485][probe] requires containment of memsz in one declared segment. That predicate ignores permission flags. These checks do not require a unique TLS ID, TLS address within its own module's base/size, an explicit TLS alignment or readable template pages at use. The selected protection phase later applies segment flags before setters/calls. Thus declared containment is not readable-live-template proof. The metadata checks also permit memsz0/filesz0, which cannot supply an admissible getter offset. No actual metadata/image is supplied.

Only under `native_libc = linked && !strict_imports && (capabilities&1)` does the [setter loop:555–566][probe] configure nonzero-ID modules in table order; it also checks each init is in an executable segment. All module setters precede main attach, procparam setup and the selected initializer loop. Duplicate IDs overwrite that slot in table order; no uniqueness/generation check was found in these bounds. Module0 skips its TLS setter, rather than clearing a slot. This is a bounded source order, not an audit of initializer behavior, module loading/unloading, callbacks or every possible setter caller. ## Admission → allocation/copy → cached lookup

[Getter:57–68][runtime] first short-circuits null index, out-of-range module, null current configured data or offset≥current memsz to diagnostic/exit21. Non-null does not prove readable index/config/source pointers. It treats index[0] as slot and index[1] as a byte offset because the cached base is unsigned char*. It checks a starting offset only; it receives neither requested access width nor alignment.

On a null block slot for this calling host thread and ID, it stores calloc(1,current memsz) in that slot. Null allocation exits1. Otherwise it copies current filesz bytes from the borrowed template into that allocation, then returns base+offset. With the positive premises and no later byte mutation, bytes0..filesz−1 equal template bytes at this copy phase and the remainder through memsz−1 is zero. Assignment of the pointer precedes memcpy in source; an interrupted/invalid copy is not a completed initialized-block proof. The implementation provides no recoverable error return, initialized flag or local rollback path.

A cache hit still evaluates current module data and memsz at admission, but does not allocate, zero or copy template bytes. Valid caller writes in a host thread's cached block survive later hits. Template mutation ordered between calls can affect a previously unused host thread's first copy while leaving an older cached copy unchanged. No-template-byte reread on a hit is **not template/global-config retirement permission**: the gate still evaluates the pointer value and fields, whose validity and ordering remain required. A stale pointer value after its pointee lifetime ends does not gain a defined outcome merely from the non-null test. This dossier recommends keeping valid template/configuration alive and stable for the whole fixed-configuration use interval.

The cache is one host-language _Thread_local pointer array per actual host thread, indexed by slot. Successful allocations for different live host threads or different slots are independent nonoverlapping allocations under the host allocation premises. There is no selection by GuestThread pointer, guest handle, TCB, GS or DTV. Calls on one host thread share its slot even if an external scheduler changes guest identity; multiplexed guest TLS would require a separate contract. A newly started thread has its own initially null array, not a generation-safe continuation of a numeric pthread identity. Source declares no module-level alignment field and uses ordinary calloc, so over-aligned TLS and typed accesses at misaligned offsets are unqualified.

## Reconfiguration and reclamation boundary

A later ordered setter replaces only global fields. It neither visits other host threads nor replaces, sizes, copies, clears, frees or generation-tags their blocks. A fresh host thread first allocates using the new configuration; an old one keeps its prior block. Equal module ID or equal template address is not proof of the same generation. Changed data with equal size leaves old bytes for old threads. Shrinking changes rejection despite physically retained bytes. Growing changes admission without growing old blocks; no actual allocation length is retained beside the pointer.

For a concrete nonexecuted countermodel: old successful block32; ordered setter now describes another live valid template with memsz64; old thread requests offset48. Current-field admission is true, allocation/copy is skipped, and the source reaches base+48. Because this is beyond old block32's one-past bound, C does not promise a defined returned pointer; **no valid return, crash or deterministic byte is predicted**. At offset32 exactly, pointer construction may produce old one-past under the stated allocation premises, but no byte access is permitted, despite current offset<64. A fresh thread with a successful64-byte allocation can validly use byte48. This clean phase distinction rejects the claim that current metadata alone bounds the actual cached block.

Neither the setter nor selected getter has an explicit free/reset/destructor hook. The selected [host_start return, join/detach and explicit exit:220–227,260–285][thread] has no module-block reclamation call; static GuestThread TLS is different storage. host_start invokes guest key cleanup, which can call external destructors and is not a proven module TLS ownership mechanism. This is absence of automatic module cleanup in these selected paths, not a global proof that no caller can free a returned heap pointer. External free, callback side effects and concurrent escaped-pointer access are excluded from the positive contract.

The C pointer array's lifetime ends on host-thread termination; the separately allocated storage is not thereby deallocated. Selected code retains allocations without an automatic release path; losing the only retained pointer can leave them unreachable. This is a source-level reclamation gap, not measured leak accounting, a whole-process/OS release claim or permission to access another thread's TLS object. An escaped heap-block pointer and access to the expired thread-local array are distinct objects/lifetimes. Validity of an escaped block still needs actual allocation lifetime and synchronization; thread join alone grants no module-generation lease, reset or unload/destructor completion. C++ thread-local destructors, original-console DTV/dynamic TLS, module initialization/unload and all host termination paths remain outside this proof.

## Maintainer decision and next discriminator

Disposition: KNOWLEDGE_REFERENCE for one fixed module2..7 configuration per host thread; DEFER full dynamic TLS/reconfiguration/unload. The missing premise controlling reuse is an actual adapter/caller contract that binds the two-word descriptor, template/configuration lifetime, host-thread identity, allocated extent/generation and requested access type/width. Neither selected linked metadata nor a cached pointer supplies it. Keep existing TCB/GS/DTV and import results within their original scopes.

A separately authorized future non-game experiment could first qualify one real adapter under stable live config, checking the public byte positive at first-copy/cache-hit/two-host-thread phases. Then an ordered equal-size reconfiguration can discriminate old cached content from fresh-thread content without invalid pointer arithmetic. Observe allocations, copies and block identity rather than merely a return flag. A separately checked safe extent observation could establish that grow admission retains the old allocation; do not execute out-of-object pointer arithmetic to manufacture a failure. Contradictory module/offset/current-data fields must be bound to the correct phase. This proposal supplies no fixture bytes, program or execution authority.

Outcome branches: matched valid first copies and independent host blocks support that adapter's bounded fixed-config byte behavior; retained old content after ordered equal-size replacement rejects generation-aware refresh; rejection after shrink confirms current-gate applicability rather than resize; retained old extent after grow rejects a current-metadata safety inference; absent adapter/ABI/extent/lifetime evidence leaves typed access and unload UNKNOWN. Stop at this frozen source contract and uninvolved independent review. Findings return to the same author in linked versions and same reviewer for affected recheck. No private/game input, source import, upstream execution/build/script, compiler/assembly oracle, allocation/pthread/syscall/native/runtime/device/UI test, generated fixture, new reader/framework/model shopping or publication/merge authority.
