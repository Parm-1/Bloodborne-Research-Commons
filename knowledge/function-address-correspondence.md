# Function-address correspondence: bbport and bbhost

**2026-10-12; SOURCE_INSPECTED, not executed.** Two addresses differing by `0x400000` can identify the same original-image address point only after image identity and coordinate/mapping premises are established. No callers says nothing decisive about reachability, decompilation completion or runtime equivalence. This guide answers [Issue #7](https://github.com/Parm-1/Bloodborne-Research-Commons/issues/7) using two pinned producers. ## Record first, convert second

For each report, retain this small task record; it is a prerequisite checklist, not a new database. Producer commit/blob identifies the tool, **not the executable**.

| Required field | What to retain / why |
|---|---|
| Original image identity | Exact input-file digest, build/region/version and derivation/view description; both reports must establish the same original bytes. A build label alone is insufficient. No executable is acquired here. |
| Producer and observation | Project, commit, path/blob, operation, raw report and whether it reads original file, analysis view or loaded/patched memory. Preserve provenance rather than replacing raw values with normalized ones. |
| Coordinate and mapping | File offset, ELF VA, kit BN coordinate, Ghidra coordinate or runtime pointer; explicit base/actual slide and the relevant ordered program-header mapping (`p_offset`, `p_vaddr`, `p_filesz`, `p_memsz`, flags). A bare “RVA” is UNKNOWN until its origin is defined. |
| Address and extent | Raw start, size/end and units; table/FDE location and encoding, segment, any duplicates/overlaps, source range and target-selection window. Separate address point from extent. |
| Conversion receipt | Formula, domain, inverse and file-offset agreement; no underflow, overflow, ambiguous mapping or out-of-file span. Record the decision and its precise claim scope. |

Use `V` for ELF VA, `O` for file offset, `B=0x400000` for this kit's base, `G=0x800000000` for the selected Ghidra convention and `S` for the **actual** runtime slide. The formulas below are source-faithful; safe domain checks are consumer obligations unless explicitly listed as guards below.

| Producer / coordinate | Transformation and restricted domain | Inverse / limit |
|---|---|---|
| bbport `callgraph.py`: start, site, caller, LO/HI | Outputs `V`; table start=`header_VA + signed loc`; site=`text_VA+i`. No base adjustment or digest gate. | Interpret LO/HI in the same ELF VA system. File mapping assumed by this script for FDEs is `O=V-text_VA+text_offset`. |
| kit `file_at(bn)` and `text()` | BN=`V+B`; `file_at` subtracts B then chooses the **first** file-backed PT_LOAD containing V: `O=p_offset+(V-p_vaddr)`, with `p_vaddr <= V < p_vaddr+p_filesz`. `text()` returns first executable PT_LOAD's file-sized `[V+B,V+p_filesz+B)`. | `V=BN-B`; `V=p_vaddr+(O-p_offset)` only in that same segment's file span. Memory-only tail (`p_filesz <= V-p_vaddr < p_memsz`) has no original-file byte mapping. |
| kit `functions()` | Table start V becomes `Function.bn=V+B`; size is a byte range, unchanged by base addition. | An absent entry does not invalidate a supported point mapping; it leaves unwind extent/entry identity UNKNOWN. |
| `addr.h` helpers | `elf_from_ghidra(A)=A-G`; `guest_from_elf(V,S)=V+S`; combined helper composes them. The selected source declares these conventions for its known build. | Check the documented view/base before subtraction; helpers use unsigned arithmetic and do not guard domains or wrap. V is not generally “offset from the lowest segment.” |
| loader/memory versus kit `at(bn)` | Loader copies each PT_LOAD to `S+p_vaddr`; `guest_ptr(mem,A)=mem.base+(A-S)`. `guest_alloc` may change S from the preference. Kit `load()` requires S=B; `at()` only casts BN to pointer. | Runtime V=`A-S` under that actual mapping and live allocation. `at()` performs no load, bounds or validity check. S=B is required by this test kit, not a universal runtime fact. |

These operations are traced in [scanner 10–26, 29–67](https://github.com/deadinside28/bloodborne_pc/blob/3c57da4198ad62039f63f33bfd205b9916518acf/tools/re/callgraph.py#L10-L67), [kit 41–71, 95–166](https://github.com/droogie/bbhost/blob/566184a74f071166299bb656c4af479e5bbe2771/tests/decomp/eboot_kit.cpp#L41-L166), [kit load/stub 181–224](https://github.com/droogie/bbhost/blob/566184a74f071166299bb656c4af479e5bbe2771/tests/decomp/eboot_kit.cpp#L181-L224), [header 27–77](https://github.com/droogie/bbhost/blob/566184a74f071166299bb656c4af479e5bbe2771/tests/decomp/eboot_kit.h#L27-L77), [address helpers](https://github.com/droogie/bbhost/blob/566184a74f071166299bb656c4af479e5bbe2771/src/engine/addr.h#L5-L27), [allocation](https://github.com/droogie/bbhost/blob/566184a74f071166299bb656c4af479e5bbe2771/src/core/memory.cpp#L17-L58), [pointer helper](https://github.com/droogie/bbhost/blob/566184a74f071166299bb656c4af479e5bbe2771/src/core/memory.h#L24-L26), [loader mapping](https://github.com/droogie/bbhost/blob/566184a74f071166299bb656c4af479e5bbe2771/src/core/elf.cpp#L111-L180) and [relocation/TLS/entry](https://github.com/droogie/bbhost/blob/566184a74f071166299bb656c4af479e5bbe2771/src/core/elf.cpp#L234-L338).

The kit's `bytes()` caches and checks SHA-256 against the constant in `addr.h`; missing/wrong input exits 77. The loader later reopens the path, records its own digest and maps/relocates it; do not infer that a mutable path still has the cached bytes. Bind a runtime report to the loaded image digest and actual slide. Relocations, import binding, optional TLS rewriting and test `stub()` patches create a changed view. Original address correspondence can survive a recorded view change; byte equality, replacement behavior and observed execution require separate evidence.

## What the function producers actually validate

| Property | bbport scanner | bbhost kit |
|---|---|---|
| Segment/table choice | First executable PT_LOAD; first PT_GNU_EH_FRAME. FDE file offset computed through the code segment even if an FDE lives elsewhere. | First executable PT_LOAD for text; **last** PT_GNU_EH_FRAME VA for table; FDE reads use first containing file-backed PT_LOAD of any flags. |
| Header/table decoding | Assumes 56-byte program headers, fixed count/table offsets and 32-bit fields. Signed count, signed table deltas, signed size at FDE+12. | Assumes 56-byte headers; checks nonzero hdr and pointer/count/table encodings `0x1b/0x03/0x3b`. Unsigned count, sign-extended 32-bit table deltas; checks FDE pc_begin=`fde+8+signed field` equals table start. Unsigned size at FDE+12. |
| FDE validity | Does not check header encodings, FDE begin, CIE or actual FDE field encoding. | Checks begin agreement, but does not parse CIE, FDE length, actual pc encoding or header version; fixed FDE layout remains a known-image assumption. |
| Bounds and failure | No image hash, ELF magic/class/header-span, complete table/FDE, size-positive, executable extent, duplicate or overlap validation. `struct.unpack_from` may fail; code slice can silently shorten; arithmetic can address an unrelated file span. | Digest is a strong known-input gate, not general ELF validation. `read<T>` returns zero if unmapped or beyond total file bytes; it checks only start's segment and total-file read span, not whole read inside that segment. `file_at` checks only mapped start, not total file size or requested extent. Program headers are unchecked memcpy reads. No comprehensive table/FDE/extent validation or wrap guards. |
| Ordering / identity | Sorts `(start,size)` tuples. Duplicate starts survive in `inner`; `sizes=dict(funcs)` retains the last (largest sorted) size. `owner` selects last predecessor by `bisect_right` and checks only its end. | Keeps table order, despite header's “address order” description. Does not sort, deduplicate or reject overlaps. Header's “162,959 / every function” is PROJECT_REPORTED, not a measured completeness result here. |

Primary parsing bounds: [scanner 10–35, 50–67](https://github.com/deadinside28/bloodborne_pc/blob/3c57da4198ad62039f63f33bfd205b9916518acf/tools/re/callgraph.py#L10-L67), [kit parsing](https://github.com/droogie/bbhost/blob/566184a74f071166299bb656c4af479e5bbe2771/tests/decomp/eboot_kit.cpp#L41-L166), [header descriptions](https://github.com/droogie/bbhost/blob/566184a74f071166299bb656c4af479e5bbe2771/tests/decomp/eboot_kit.h#L33-L49). Do not generalize these parsers to arbitrary malformed/truncated ELF. Neither establishes that every logical routine has one FDE, that every extent byte is an instruction, that all entries are known, or that an unwind entry proves a replacement correct.

The one additional consumer, [insn_eboot_test.cpp 16–103](https://github.com/droogie/bbhost/blob/566184a74f071166299bb656c4af479e5bbe2771/tests/decomp/insn_eboot_test.cpp#L16-L103), passes `f.bn` to `file_at`, prints/dumps that same BN coordinate with `f.size`, and uses BN in relocation arguments. It tries decoding to an end or inferred table and tests entry relocation. Reading its source supplies coordinate provenance, **not** a successful decoding result, validated range or decompilation percentage. It does not independently establish full file-backed extent safety after `file_at`.

## Decision and claim scope

| Decision | Required observation | Permitted conclusion / limit |
|---|---|---|
| `JOIN_SUPPORTED_UNDER_PREMISES` | Same established original digest/build/view; documented coordinate origins; reversible conversion with consistent unambiguous segment/file mapping and no wrap; normalized points equal. | Same original-image address point. With compatible validated table/FDE extents, also the same described extent record. Logical routine identity needs additional entry/symbol/disassembly evidence; runtime/replacement equivalence needs its own contract and observations. |
| `CONFLICT` | Established unequal image digests/builds for a same-image claim, unequal normalized points, contradictory file/segment mappings, or incompatible claimed extents. | Reject the disputed same-image/point/extent claim. Equal starts with unequal sizes conflict **for extent**, while a supported point join can remain. Changed-view bytes conflict with an original-byte-equality claim, not automatically with original address correspondence. |
| `UNKNOWN` | Missing digest, coordinate origin, actual slide, required mapping, unreadable/unrecognized metadata, ambiguous overlaps/duplicates or no entry evidence. | Stop the unsupported claim and name the missing premise. No digest is not permission to subtract B. No unwind entry or first-segment omission is not evidence that two otherwise proven address points differ. |

A justified match does not imply whole-game function identity. A justified rejection must target the claim actually contradicted: different displayed bases alone, absent scanner callers, missing FDEs or a later code segment cannot falsify a valid same-image address-point conversion.

## Original hypothetical examples — NOT game records

All metadata/bytes/counts below are invented here. They are arithmetic/source reasoning, not outputs from either tool. Hypothetical digest H=`"aa" repeated 32 times`, J=`"bb" repeated 32 times`; neither represents the kit's accepted executable. The actual kit rejects arbitrary hypothetical images at its digest gate. These examples illustrate admissible formulas and producer limitations, not executed positives.

1. **Positive, including inverse.** Two consumer-supplied original-file reports establish digest H/build Q and segment `p_offset=0x1000, p_vaddr=0x2000, p_filesz=0x300, p_memsz=0x400, PF_X`. Scanner start V=`0x2120`, size=`0x20`; kit-style BN=`0x402120`, same validated extent. BN-B=`0x2120`; file O=`0x1000+(0x2120-0x2000)=0x1120`; inverse `0x2000+(0x1120-0x1000)=0x2120`. End V=`0x2140` and O=`0x1140` stay inside file/executable spans. Ghidra-style A=`0x800002120`; runtime A at separately established S=`0x700000` would be `0x702120`. For an original hypothetical unwind row, header V=`0x2280`, signed loc=`-0x160` and signed FDE delta=`-0x40` yield start `0x2120` and FDE `0x2240`; FDE begin delta=`-0x128` yields `0x2240+8-0x128=0x2120`, and range field=`0x20`. Both producers can agree under their respective validated/assumed layout premises. A range field `0x80000000` instead becomes scanner size `-2147483648` versus kit size `2147483648`; neither is a justified small executable extent. Point and compatible extent: `JOIN_SUPPORTED_UNDER_PREMISES`; logical routine and runtime behavior still require evidence.
2. **Identity / segment negatives.** Same numbers with digest J/build R versus H/Q: `CONFLICT` for same original image. Missing either digest: `UNKNOWN`. If the second report claims O=`0x1220` for V=`0x2120` in the positive segment, the claimed mapping conflicts by `0x100`. If its actual segment offset is `0x1100`, it is a different mapping premise requiring resolution; do not conceal it by subtracting B.
3. **Extent versus point.** Same proven H/Q point, but sizes `0x20` and `0x30`: same-point join remains supported; same-extent claim is `CONFLICT` (ends `0x2140` / `0x2150`). Duplicate rows `(0x2100,0x20)` and `(0x2100,0x40)` yield two scanner range entries with displayed size `0x40`, not two proven routines. Overlap `[0x2100,0x2200)` and `[0x2180,0x2190)` at site `0x2195` selects the latter predecessor and returns no owner, despite containment by the earlier interval. Identity/attribution is `UNKNOWN` until resolved; kit supplies no overlap resolution either.
4. **Raw false site / omitted edge.** Invent an embedded data span at V=`0x2100` beginning `E8 1B 00 00 00`, inside a source FDE, targeting the invented function start `0x2120`: `0x2100+5+0x1b=0x2120`. Raw scanner logic would accept this candidate even if instruction-aware evidence establishes it is data. Replace E8 by E9: same target, jump candidate rather than call. An indirect `FF D0` call at a known instruction boundary is invisible to this E8/E9 scanner; neither a candidate nor no hit proves actual execution or nonexecution.
5. **Boundaries / alternate segments.** For N=`0x300` bytes, starts `0..0x2fa` are scanned, but valid five-byte start `0x2fb` is omitted. A target exactly HI or site exactly FDE start+size is excluded by the respective half-open check. Positive segment V=`0x2300` is at file end: no file byte, but remains inside memory size up to `0x2400`; `file_at` is null for the file tail. A later executable PT_LOAD at `0x5000` is outside scanner code coverage: a proven point there can still join; no scanner edge is UNKNOWN for reachability. Missing table entry means no target hit, not no routine. Unrecognized encodings cause kit exit 1; a truncated read may become zero rather than a validated absent entry. Metadata readability must be separately established.
6. **Misleading counts / output truncation.** Invent 23 sites from 21 outside caller starts and two inside sites from one inside caller: sites=`25`, ext_fns=`21`, int_fns=`1`. Only first 20 sorted ext addresses appear on that per-function line; `.callers` contains all 21 if those are the whole outside union. Several sites and E8/E9 from one caller deduplicate in sets. Across callees, `distinct outside callers` is a union, not a site count or sum of ext_fns. Duplicate target rows inflate `functions in range` and may repeat `called from outside`; these are row/count semantics, not coverage.

## Finite workflow for one address report

Task: “Does scanner `0x2120` with no callers correspond to kit-style `0x402120`, and can I replace it?”

1. Consult the pinned scanner for ELF VA output and the kit/helper source for BN origin. Retain the original records. Request consumer-supplied digest/build/view and segment/FDE provenance for both; if unavailable, return `UNKNOWN: original image identity or coordinate mapping missing` and stop this join.
2. Under the positive example's premises, perform BN-B and the segment inverse. Return `JOIN_SUPPORTED_UNDER_PREMISES` for the point, and only for extent if both records' validated start/range agree. If point/segment/digest disagree, return the specific `CONFLICT`; if extent is ambiguous, retain the point result and stop extent identity with `UNKNOWN`.
3. Read [RC-0003](../claims/RC-0003-callgraph-limits.md) for what no callers and candidate hits mean. Do not infer unreachable code, completed decompilation or suitable replacement. No universal constant or graph percentage resolves these questions.
4. For a decoded edge, external evidence would need the same authorized original bytes/view, trustworthy instruction boundaries and decoding/control-flow attribution (including data and indirect edges). For observed execution or replacement equivalence, a separately authorized consumer needs loaded digest/slide/patch history, ABI, inputs/state/path and attributable runtime/comparison observations. Acquire none here; absent those, stop the stronger claim with `UNKNOWN` and its exact missing evidence.

**Reuse:** KNOWLEDGE_REFERENCE, with existing [source/license decisions](../sources/projects.yaml); no upstream code import or license conclusion. **One next decision:** a contributor with an actual public address-report task chooses whether to supply the identity/mapping record and apply this two-producer contract, or retain it as a reference. [One focused frontier](../frontiers/function-correspondence.md); no automatic runtime campaign.
