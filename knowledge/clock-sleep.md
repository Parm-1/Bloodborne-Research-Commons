## Clock domains and process origin

[Clock mapping/read:51–93][kernel] selects these **host** domains. The aliases in comments describe names, not separate implementations or console fidelity.

| Guest ID | Selected host domain | Basis and output |
|---|---|---|
| 0,9,10 | CLOCK_REALTIME | Epoch seconds/nanoseconds; adjustable wall time |
| 4,5,7,8,11,12,16,17,18,19 | CLOCK_MONOTONIC | host monotonic basis; UPTIME/network aliases gain no special network/raw/suspend behavior |
| 13 | CLOCK_REALTIME_COARSE | wall sample, then nsec forcibly0; whole-second output |
| 14 | CLOCK_THREAD_CPUTIME_ID | CPU consumption of the calling host thread |
| 2,15 | CLOCK_PROCESS_CPUTIME_ID | CPU consumption of the host process, including its threads |
| other uint32 IDs, including1,3,6 | rejected | EINVAL before host read/output write |

The Linux description says monotonic time excludes suspend, can be rate-adjusted, and successive reads can be equal; it is not MONOTONIC_RAW or BOOTTIME. CPU clocks count consumption rather than a sleeping thread's elapsed deadline. Host process CPU time is not isolated guest CPU time. Wall and monotonic values cannot be subtracted merely because both use sec/nsec. Matching monotonic aliases can support a same-domain interval under successful samples and a common host clock instance, but their separate calls are separate instants. The source does not supply cross-domain calibration or an atomic paired sample.

`clock_read` checks clock_gettime before writing guest output. SCE errors return raw32 `0x80020000 | guest_errno`; POSIX errors return-1 and store a mapped int32 in `runtime_errno()`. Invalid ID/null ts maps22. SCE clock errors do not update guest TLS errno. `clock_getres` calls the selected host getres, allows null output and copies the host result unchanged: ID13's returned host resolution does **not** describe its additional whole-second truncation. Resolution is not actual accuracy or a guaranteed increase on each read. Guest errno is a `_Thread_local int32_t` in runtime_thread.c; success does not clear it. The mapping includes host EINTR→4, EINVAL→22, EAGAIN→35 and unmapped→5; these are guest mappings, not Linux numeric errno equality.

The `process_start` static timespec is sampled by a constructor, independently of `runtime_start`; the latter does not reset it. This is elapsed monotonic time from that loaded producer's constructor sample, not process CPU consumption, guest boot time, a wall epoch, or a cross-run origin. The constructor read is unchecked; static zero initialization is not a valid startup receipt. Later process reads are also unchecked and their local samples can be uninitialized on failure.

For valid normalized samples and signed native subtractions that are representable, write Δs=current.sec-start.sec and Δn=current.nsec-start.nsec. Counter returns `(uint64(Δs)*10^9 + uint64(Δn)) mod 2^64`; ordinary borrow is recovered by unsigned addition, so a nonnegative mathematical elapsed nanosecond value below2^64 is returned exactly. Microseconds instead return `(uint64(Δs)*10^6 + uint64(trunc(Δn/1000))) mod 2^64`. For negative Δn with a fractional microsecond, truncation toward zero makes this one greater than floor(elapsed_ns/1000). It is not universally `counter/1000`. These equations do not repair overflow in the signed subtraction before the casts. Frequency1,000,000,000 supplies the counter scale, not one-nanosecond resolution or TSC frequency. Across instances/reloads, matching scales do not preserve the constructor origin.

## TSC and actual public consumers

[TSC:94–110][kernel] returns bare `__rdtsc()` without explicit fences. Intel describes RDTSC as reading a64-bit counter without serializing prior/subsequent instructions; its ordering guidance distinguishes loads from stores. This source contains no CPU feature/permission, invariant-rate, migration/cross-core synchronization, hypervisor or compiler-ordering qualification. It does not establish a wall/monotonic epoch, CPU work completion or the CPU's current execution frequency.

`tsc_frequency` lazily caches a plain uint64. Its source order is monotonic a; TSC t0; one requested20,000,000ns host nanosleep; monotonic b; TSC t1. It checks none of those host results, retries no EINTR, uses measured `ns=(uint64(Δs)*10^9+uint64(Δn)) mod2^64`, and caches `((t1-t0)*10^9 mod2^64)/(ns ? ns : 1)`. Interrupted sleep does not force a20ms denominator; failed clocks can invalidate samples. Multiplication wraps **before** division. The ns0→1 fallback avoids zero division, not a meaningful interval. A cached0 causes recalculation on the next call; nonzero values persist without revalidation. Concurrent unsynchronized first use/read/write can be a C data race, not a defined calibration schedule. A single-thread/externally ordered positive requires valid clock/TSC samples, no unintended modular loss and the separate rate/ordering premises; the formula alone proves no hardware accuracy.

This is a different producer from the kernel bare intrinsic; it is not an automatic full C/C++ memory-order or store-completion proof. [One flip-status writer:733–745][driver] writes process_time then tsc while holding its port mutex. These are successive fields, not an atomic cross-clock conversion or a proved GPU completion timeline. No broader VideoOut correctness or target execution is studied.

## Sleep phases, errors and diagnostics

[Sleep:112–138][kernel] converts uint32 usleep to ns by multiplication1000; uint32 sleep seconds by10^9 (both fit uint64). Valid nanosleep requires non-null rq, sec>=0 and0<=nsec<10^9. It converts sec*10^9+nsec in uint64 without an overflow check; native time_t/long casts then need representability. It takes no absolute deadline. Stable request storage is required; input fields are read more than once.

`sleep_ns` constructs a relative native timespec, samples monotonic a, and calls host nanosleep with the **same local t as request and remainder**. EINTR retries the returned remainder until a call succeeds or a non-EINTR error breaks the loop. No retry bound or progress guarantee is implemented. Under the separate Linux contract and valid native storage, an eventual host success supports completion of that sequence of relative sleeps. Handler/restart overhead, rounding and scheduling can extend elapsed time; no exact duration, upper bound or application predicate follows. This differs from host POSIX-facing nanosleep's normal exposed EINTR/remainder and sleep's unslept-seconds interface; the wrapper consumes interruptions internally.

After the loop, helper reads b, updates diagnostics and returns the last non-EINTR host error or0. **All selected wrappers ignore that helper result.** SCE/POSIX usleep and POSIX sleep return0; valid POSIX nanosleep writes rem={0,0} if provided and returns0 even after host error. SCE nanosleep wraps that POSIX result, so invalid-input -1/TLS22 becomes raw32 `0x80020016`; valid-input host failure still becomes0. Validation failure occurs before the helper, leaves rem unchanged and records no helper sleep. Valid returns do not clear guest TLS errno or map discarded host errno. Non-null invalid guest pointers may fault; they are not a defined EFAULT control. Cancellation, signals that do not return, faults and nonlocal exits are outside the normal-return contract.

Diagnostics are a different observation. a→b includes sleep/retries/handler and scheduling overhead between those samples, not requested ns, time spent exclusively blocked, or wrapper-entry→return (post-b instrumentation is excluded). Reads are unchecked; signed sec-difference*10^9+nanodifference can overflow before its uint64 cast. No duration is inferred from failed/indeterminate samples. Once the helper reaches these updates, it increments sleep_calls once even after host failure and after multiple EINTR attempts, adds measured ns, then calls wait_note(kind3). `runtime_sleep_stats` exchanges the two atomics separately; concurrent snapshots can split one call's count and duration across reports. Atomicity of individual counters does not make a transactional pair or a per-caller completion receipt. Wait-note has plain shared initialization/metadata accesses; conflicting unsynchronized use is not a defined positive. [Frame diagnostic consumer:672–678][driver] divides aggregates by frames; its label and the polling comment are not independent game observations.

## The two timeval routes

[runtime_time:11–24][time] exact `n88vx3C5nW8#I#J` wins before name fallback. It calls host gettimeofday(&t,&z), stops with exit21 on host error (no guest TLS error return), copies optional timeval/timezone outputs and returns0. The kernel fallback for `n88vx3C5nW8#p#J` calls gettimeofday(&t,NULL) unchecked; optional timezone uses time/localtime_r unchecked and computes minuteswest from tm_gmtoff with dsttime0. Kernel `sceKernelGettimeofday` rejects null tv with raw32 `0x80020016`, otherwise uses that fallback. Exact route allows null tv. Source does not validate writable outputs. If a failed host call leaves local fields indeterminate and they are copied, no defined normal return or successful sample is claimed.

The Linux description places timeval in wall/Epoch seconds and microseconds, subject to wall jumps; timezone is obsolete and libc-dependent (glibc/musl ignore the timezone argument). Thus a successful exact host return does not itself establish initialized meaningful z fields on every libc; copying indeterminate z is not a defined positive. Neither timezone path is a monotonic offset conversion. Keep the two resolver/error contracts distinct even though both output two int64 timeval fields.
